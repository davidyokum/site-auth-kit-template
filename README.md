# site-auth-kit-template

The starter site for David Yokum's websites: a small, real Next.js 16 (App Router) site on AWS Amplify Gen 2, wired to [auth-kit](https://github.com/davidyokum/auth-kit). It meets the login standard out of the box (passkey-first sign-in, server-side checks on every route, an admin area with an append-only log, and a localhost kit for signing in as test personas) and the tests fail if a change breaks it.

> Pre-release, like auth-kit (`v0.1.10-alpha.1`). A private demo made from it has run on Amplify since 2026-10-17 and follows the template's upgrades (on auth-kit `v0.1.9-alpha.3` since 2026-10-19): see [Verified on a live deploy, and what's left](#verified-on-a-live-deploy-and-whats-left).

Comments cite the login standard as "03 §2" (its rules) and "03 §1" (its tiers). The standard itself is kept privately; [auth-kit's README](https://github.com/davidyokum/auth-kit#how-the-standard-maps-to-the-code) maps every rule to the code that enforces it.

## Roles

Every site has the same site-wide admin roles (auth-kit [ADR 0020](https://github.com/davidyokum/auth-kit/blob/main/docs/decisions/0020-site-wide-roles.md)). Each role includes everything below it.

| Role (as screens show it) | Group | View everything | Edit any content | Manage people | Security, exports, deletion | Owner-only pages |
|---|---|---|---|---|---|---|
| Owner (only one) | `owner` | Yes | Yes | Yes, everyone but themselves | Yes | Yes |
| Super admin | `superadmin` | Yes | Yes | Roles below Super admin | Yes | No |
| Admin – content & people | `admin-content-people` | Yes | Yes | Roles below their own | No | No |
| Admin – content only | `admin-content` | Yes | Yes | No | No | No |
| Admin – view only | `admin-view` | Yes | No | No | No | No |
| Member | (no group) | Their own account and items | Only items they've been given access to | No | No | No |

- **One owner.** The owner role is never granted, not even by the owner. It moves only by **Transfer ownership…** (in the role picker, owner only): to someone who has signed in, with a reason, their address typed out, and a recent sign-in; both of you are emailed, and you become Super admin. Nobody can disable, demote, or delete the owner, and the invite-expiry schedule never disables them. The People page flags a site with no owner, or more than one.
- **Grants go down, never sideways or up.** You grant, and act on, only roles below your own, so only the owner grants Super admin, and Super admins can't manage each other. Nobody changes their own role. Every grant needs a reason and a recent sign-in; a Super admin grant also emails the owner.
- **Admin – view only and Admin – content only** open the admin area and the Activity log and see the People list, but can't change anyone.
- **Members** aren't admins. What they can see and do with a particular project is decided on that project, with a resource role ([Projects](#projects-access-to-one-item)), never by these roles. On every project the site role is a floor: Admin – view only sees it, Admin – content only also edits it, Admin – content & people and above also choose who has access.
- The People page's role picker shows each role's can and can't, a **Compare roles** grid (this table, from auth-kit's `ROLE_MATRIX`), and the note "These roles are for running the site. Access to individual projects, plans, and other items is managed on each one.", linked to the projects, with the three resource roles summarized under it. Group names appear only in `lib/capabilities.ts`.

## Projects: access to one item

The sample feature is projects, and each project has its own people (auth-kit [ADR 0022](https://github.com/davidyokum/auth-kit/blob/main/docs/decisions/0022-resource-roles.md)). Screens use the item's own word ("Who has access to this project"); code calls these resource roles.

| Role on a project | Can | Can't |
|---|---|---|
| Manager | See and edit it, choose who has access, invite someone new to it | Remove the last Manager (every project keeps at least one) |
| Contributor | See and edit it | Change who has access |
| Reader | See it | Edit it or change who has access |

On any project, a person gets whichever allows more: their role on it, or their site role, which counts on every project (Admin – view only: see; Admin – content only: see and edit; Admin – content & people, Super admin, Owner: see, edit, and choose who has access).

- **Who creates projects:** site admins who manage people, choosing each one's Manager (themselves by default). Members see only the projects they have a role on. Two switches in `lib/resources.ts` change that per type: `selfServiceCreate` (any member creates one and becomes its Manager) and `sharedDirectory` (everyone signed in sees every project, read-only). Both are off.
- **`/app/projects`:** your projects (`auth.listMyResources`), or every project for a site role that sees them all, each with your role; the create form if you may create.
- **`/app/projects/[id]`:** `pages.requireResourceRole('project', id, 'view')` before anything is read, so anyone without access gets "not found". The edit form if you may edit (saved with `requireResourceRole(…, 'edit', { live: true })`, audited, and refused over someone else's newer edit). **Who has access** (auth-kit's `WhoHasAccess`): Managers and site admins who manage people add someone by email with a role picker that says what each role can and can't do, change roles, and remove people; anyone with a role can leave. The last Manager can't leave or be demoted, unless a site admin names the new Manager in the same step.
- **Inviting someone new:** a Manager can invite an address with no account. It's a member-level account (no admin role) with access to that one project; the site's admins who manage people get an email about every such invite, and if that email can't be sent, the invite is undone.
- **Every access change is audited**, intent before and result after, naming the person and the project; the Activity page shows them by the project's current name (`app/admin/activity/page.tsx` looks names up; each row also keeps the name it had). Screens never show a project's ID. Disabling someone on the People page removes their project roles too; a project left without a Manager is listed in that entry, and admins who manage people can make someone its Manager.
- **Data:** `amplify/data/projects-table.ts` holds the projects; auth-kit's `ResourceAccessTable` (in `amplify/backend.ts`) holds who has which role, with point-in-time recovery and deletion protection. The compute role gets exactly the calls each store makes.
- **API:** `GET`/`POST /api/projects`, `GET`/`PATCH /api/projects/[id]`, `GET`/`PUT /api/projects/[id]/access` (`PUT { email, role }` gives an existing account a role, or changes it).

**Sample personas:** `personas.json` has three members named for the roles, `manager`, `contributor`, and `reader`. After `npm run personas:seed`, `npm run projects:seed` gives them those roles on a "Sample project" in your sandbox (as Admin – content & people, audited like any change; it refuses anything but a sandbox, and running it again changes nothing), so **Sign in as…** shows each role's view.

**Your own items:** replace the projects (`lib/projects/`, `amplify/data/projects-table*.ts`, `app/app/projects/`, `app/api/projects/`) and keep the pattern: declare your type in `lib/resources.ts` (its noun is what screens say), call `requireResourceRole(type, id, …)` in every page, route, and action that takes an ID, list with `listMyResources`, create with `resourceActions().create({ type, run })` so the item and its first Manager are written together, and put `WhoHasAccess` on the item's page. Several types share the one access table.

## Account creation

How people get an account is one setting, `accountCreation` in `site.config.ts` (register D1; auth-kit [ADR 0023](https://github.com/davidyokum/auth-kit/blob/main/docs/decisions/0023-account-creation.md)). In every mode Cognito's own sign-up stays off: accounts are made on the server, the way an invite makes them (no password; the first emailed code verifies the address; then the required passkey or password plus authenticator), every new account starts as Member, and the sign-in card says which mode applies.

| Mode | Who gets an account | What the site gets | What you set up |
|---|---|---|---|
| `{ mode: 'invite' }` (default) | Whoever an admin invites from the People page, or a project's Manager invites to that project | Nothing more | Nothing |
| `{ mode: 'request' }` | Anyone may ask at `/request-access` (name, email, why); an admin approves (the ordinary invite) or declines (silently) | `/request-access` and `POST /api/auth/request-access`; the People page's **Pending requests** tab with a badge; a daily digest to the admins who manage people; the request table | `privacyNoticeUrl` (optional); `siteWaf` (optional) |
| `{ mode: 'domains', domains: ['example.org'], requestsAlso: true }` | Addresses on the list create their own account at `/sign-up`; with `requestsAlso`, everyone else can request access | `/sign-up` and `POST /api/auth/sign-up`; the preSignUp trigger (it re-checks the list); the 24-hour cleanup of never-verified sign-ups; members change their own email and delete their own account on My account; with `requestsAlso`, everything `request` gets | `privacyNoticeUrl` and `siteWaf` (both required), and the WAF smoke test after every deploy |
| `{ mode: 'open' }` | Anyone with an email address | Everything `domains` gets | The same as `domains` |

- **Only where it's on.** The account-creation pages and routes are `page.signup.tsx`, `route.signup.ts`, `page.request.tsx`, and `route.request.ts`; `next.config.ts` makes them pages only in the modes that have them (`lib/account-modes.ts`), so an invite-only site's build, route manifest, and auth matrix don't have them at all. The backend deploys each mode's tables and jobs the same way, and the matrix adds each mode's rows.
- **The same answer for every address.** Sign-up and request access answer every address alike, in at least 800 ms; an address that already has an account gets an email instead of a different screen. They're rate-limited per mailbox, per IP, and site-wide (auth-kit's limits), check the origin, and read the client's IP from the last `X-Forwarded-For` entry (the one Amplify Hosting's CloudFront appends).
- **A domain takes its subdomains**, and a bare top-level domain (`'edu'`) takes every address under it, students and alumni included. Say so on purpose.
- **Every sign-up gets the silent WAF check** (register D3; auth-kit 0.1.9): in `domains` mode as in `open`, `next dev`, builds, and synthesis fail without `siteWaf`, the sign-up route refuses posts without AWS WAF's token (except under `next dev`), and synthesis fails unless the 24-hour sweep of never-verified sign-ups is deployed (`amplify/backend.ts` deploys it on every sign-up site).
- **The site web ACL** (`siteWaf`; required on sign-up sites, optional on request sites): a CLOUDFRONT web ACL from auth-kit's `createSiteWebAcl(stack, id, { accountCreation })` (a silent challenge and a per-IP limit on posts to the two routes). Deploy it in `us-east-1` from a small CDK app of its own (one per account works, like the shared Cognito ACL; see auth-kit's README, section 11), associate it with the Amplify app in **Hosting → Firewall**, and put its ARN and its JavaScript integration URL (WAF console → **Application integration**) in `siteWaf`. The preset then gets `siteWebAclArn`, the sign-up and request pages load the integration (with the request's CSP nonce; `connect-src` allows its host), and the screens post through it.
- **After every deploy of a sign-up site:** `npm run waf:smoke -- --url https://<site>`. It posts to the sign-up route with no WAF token and expects AWS WAF's challenge (202, `x-amzn-waf-action: challenge`); the route's own answer means the ACL isn't in front of it. The app can't see the association, so this is the check.
- **Members on sign-up sites** change their own email (a code to the new address; the old one keeps working until it's verified, and is told) and delete their own account (a recent sign-in and the address typed; never the owner) from My account (`app/account/actions.ts`, auth-kit's `createSelfServiceActions`). Everywhere, the custom message trigger refuses an email change made through Cognito's own API, so the site (or an admin) is the only way.

`next dev` and every build stop with a list if `site.config.ts` lacks what its mode needs (`lib/site-checks.ts`), and auth-kit checks again at synthesis.

## The sender and the help address

**The sender** (register A10, E4a): every auth email comes from the site's reply-able `sign-in@` mailbox, never `noreply@`, under the family's sender name ("{Site} (UNC)" on a work site, the site's name alone on a personal one). auth-kit refuses anything else at synthesis and when the mailer starts.

- **The family's by default.** `email.fromAddress: null` in `site.config.ts` uses the family's shared sender from `site.families.ts`. Personal sites send only from `sign-in@yokum.app` (register F11; verified in SES in the personal account; auth-kit refuses any other address on a personal site). The work families have none, so their sites send from `sign-in@` on their own domain, which must be a verified SES identity in the account they deploy to (SPF, DKIM, and DMARC published); `npm run setup` asks them.
- **A site name outside ASCII** ("Café Reports") is fine: auth-kit writes it as RFC 2047 encoded-words, as SES requires.

**The help address** (register E4c; auth-kit [ADR 0024](https://github.com/davidyokum/auth-kit/blob/main/docs/decisions/0024-sign-in-copy-and-family-themes.md)): every site has one, a role-based mailbox, so it outlives whoever answers it. It's the Reply-To on every auth email (Cognito's code emails included), the "Help: …" line at the foot of every email, and the address the sign-in card's help screens name ("Need help with your Example Site account? Email …", "Never send a password or code.").

- **The family's by default.** `email.replyTo: null` uses the family's mailbox from `site.families.ts`: personal sites use `help@yokum.app` (live since 2026-10-19; it forwards to David). The work families have no shared mailbox yet, so their sites set their own.
- **A site's own.** Set `email.replyTo` to the site's mailbox (`'reports-help@example.org'`); `npm run setup` asks.
- **A person's own address, only on purpose**, for a site that deliberately signals it's one person (never the default): `email.replyTo: { address: 'jordan.lee@example.org', personal: true }`. Without `personal: true`, auth-kit refuses a `first.last@` address. `npm run setup` asks you to confirm it (`--help-personal` when scripted).
- **A Super admin's override, without a deploy.** Admin → **Settings** → "Sign-in help" (Super admins and the owner; `settings.security`): needs a recent sign-in and a reason, is audited, and emails the owner and every Super admin (if that email can't be sent, the change is undone). It stays on the configured address's domain (or the family's), and "Use the configured address" goes back. The sign-in page and the app's emails read the address in effect on every request; Cognito's own Reply-To and code emails keep the configured address until the next deploy. The override lives in the site settings table (`amplify/backend.ts`).
- **Required.** auth-kit refuses a missing, placeholder (`apps-help@replace-me.invalid`), or unacknowledged personal address at synthesis, and `next dev` and builds stop on one first.

`site.families.ts` keeps both family tables; since auth-kit 0.1.9 its themes carry the same addresses, and a unit test holds the two together.

## Start a new site from this template

You need Node 22, the AWS CLI signed in to the account you'll deploy to, and the sender's domain verified in Amazon SES in that account (with SPF, DKIM, and DMARC published), because auth email goes through SES. Personal sites in the personal account send from `sign-in@yokum.app`, which is verified there.

1. **Make the repo.** On GitHub, **Use this template**, or:
   `gh repo create <you>/<site> --template davidyokum/site-auth-kit-template --private --clone`
2. **Install:** `npm ci` (the lockfile pins auth-kit's release tarball by hash).
3. **Set it up:** `npm run setup`. It asks for the site's name, its family, its sender (work families only; personal sites use the family's) and help mailbox (offering the family's), how people get an account (and, for sign-up sites, the domains and the privacy notice), and the owner's email address, then writes them into `site.config.ts` and puts `personas.json` on the site's own `.test` domain. Run it again any time; every question offers the current value. It touches no AWS and never asks for a secret. Then check the rest of `site.config.ts`: invite domains, alert recipients, the card style (`cardStyle`; [The sign-in page](#the-sign-in-page-and-its-backdrop)), and the local name and port (if you change those, match the `dev` and `start` scripts in `package.json`).
4. **Say where it deploys** in `deploy.config.json`: the AWS CLI profile, the 12-digit account ID it must reach, and the user pool's web ACL (`webAcl`: the account's shared ACL; [The user pool's web ACL](#the-user-pools-web-acl)). Every AWS-touching script refuses until this is right. `amplifyAppId` stays `null` until the Amplify app exists (Deploy, step 2). The hygiene test allows the site's own account and app IDs and still fails on any other account or app ID in the repo. (Account IDs aren't secrets, but keep a public repo's copy on the placeholder.)
5. **Personas:** `npm run setup` put `personas.json` on your site's `.test` domain. Add one per app role if you have any.
6. **Your sandbox backend:** `npm run sandbox`. It checks the account, then runs `npx ampx sandbox --profile <profile>`, which deploys your own throwaway copy of the backend and writes `amplify_outputs.json`. Leave it running while you work.
7. **Seed the personas:** `cp .env.local.example .env.local`, then `npm run personas:seed`. It refuses anything but a sandbox pool, creates each persona with a password and an authenticator, and writes their secrets to `.env.local` (never printed). Then `npm run projects:seed` gives the sample Manager, Contributor, and Reader their roles on a sample project.
8. **Run it:** `npm run dev`, open http://app.localhost:3000, and pick a persona from **Sign in as…** in the blue ribbon.
9. **Choose the backdrop:** `npm run backdrop:pick` opens nine variations behind your real sign-in card; **Use this one** writes it into `site.config.ts`, locked. (Or `npm run backdrop:lock` to keep the one proposed from the site's name.) Deploys fail until it's locked.
10. **Make it yours.** Replace the sample projects with your own items, keeping the pattern ([Projects](#projects-access-to-one-item)): guards on the server, access checked on each item (`requireResourceRole`), lists from `listMyResources`, 404 for anyone without access. Add a matrix row for every page and route you add. Fill in the site record in `AGENTS.md`.
11. **Check:** `npm run check` (typecheck, lint, unit tests, build, production-build check, auth matrix).

Without a sandbox, `npm run outputs:placeholder` writes a clearly fake `amplify_outputs.json` so the site builds and the tests run, but nothing can sign in.

## Deploy on Amplify

Personal projects deploy to the personal AWS account by default; whatever the account, `deploy.config.json` names it and the scripts check it.

1. **Preflight:** `npm run preflight` confirms the profile reaches the declared account (`aws sts get-caller-identity`, read-only). It's also the first step of `sandbox`, `personas:seed`, and `preview:password`.
2. **Create the app** in the Amplify console: *Create new app* → GitHub → this repo → branch `main`. Amplify uses `amplify.yml`: each branch's pipeline deploys its own backend (`ampx pipeline-deploy`), writes `amplify_outputs.json`, builds, and fails the deploy if the build contains the localhost kit. New sites start on the default `amplifyapp.com` address. Put the app's ID (`d` and 13 letters or digits, as in `https://main.<app-id>.amplifyapp.com`) in `deploy.config.json` as `amplifyAppId`.
3. **Attach the compute role (once per app).** The backend creates the SSR compute role with exactly the permissions the server needs; Amplify doesn't attach it by itself. After the first deploy, copy `custom.computeRoleArn` from the branch's outputs (Amplify console → the branch → *Deployed backend resources*, or the stack's outputs) and set it as the app's compute role in the console (*App settings* → *IAM roles* → *Compute role*), or: `aws amplify update-app --app-id <app-id> --compute-role-arn <arn> --profile <profile>` (run `npm run preflight` first).
4. **Preview branches behind a password** (Tier 1): `npm run preview:password -- --app-id <app-id> --auto-branches` makes branches Amplify creates start behind a password; `-- --branch <name>` does one existing branch. It asks for the password without echoing it; keep it in your password manager.
5. **A custom domain, later:** add it in the console, set `APP_ORIGIN` for that branch (*Environment variables*), and then turn on passkeys: `passkeys: { relyingPartyId: '<that domain>' }` in `site.config.ts`. Passkeys wait for the final domain because changing it later forces everyone to register again.
6. **The owner** (`ownerEmail` in `site.config.ts`; once per branch pool; auth-kit doesn't bootstrap the first admin yet): create yourself the way the People page invites people, with no password and no welcome email, then go to `/sign-in`, choose **Email me a code instead**, and at "Choose how you'll sign in next time" save a passkey or set a password and an authenticator (that step is required). After `npm run preflight`: `aws cognito-idp admin-create-user --user-pool-id <pool> --username <your email> --user-attributes Name=email,Value=<your email> --message-action SUPPRESS --profile <profile>`, then `aws cognito-idp admin-add-user-to-group --user-pool-id <pool> --username <your email> --group-name owner --profile <profile>`. A site has exactly one owner: this is the only time the role is set outside the app (and the break-glass fix if a pool ever ends up with none). Everyone else comes in from the People page, and ownership moves with Transfer ownership.
7. **Choose the web ACL before the first branch deploy** (`webAcl` in `deploy.config.json`; [The user pool's web ACL](#the-user-pools-web-acl)): a branch deploy fails synthesis while it's `null`.
8. **Account creation:** a sign-up or request site deploys its tables and jobs with every branch (see [Account creation](#account-creation)). A sign-up site needs the site web ACL associated in **Hosting → Firewall**, and `npm run waf:smoke -- --url https://<site>` after every deploy.
9. **The account-change notices need nothing more:** the route ships with the site, and the rate-limit table and `ses:SendEmail` come with every branch's backend.
10. **Invite expiry runs by itself.** `amplify/backend.ts` deploys auth-kit's `InviteExpirySweep` with every branch: hourly, it disables invites still unused after 7 days, and the Activity page shows each as "Scheduled job". It never disables the owner: an unused owner invite gets a daily email to the owner (and the first `alertEmails` address) instead. Give it an `alarmTopic` (an SNS topic someone reads) so a failed run reaches a person.

Merging to `main` deploys the live site. Once it's live, work on branches.

### The user pool's web ACL

Register F7: one shared WAF web ACL per AWS account and Region (auth-kit ADR 0013), chosen in `deploy.config.json` because it's a fact about where the site deploys (`amplify/web-acl.ts` turns it into the preset's `waf`):

| `webAcl` | What the pool gets |
|---|---|
| The account's shared ACL ARN (`arn:aws:wafv2:<region>:<account>:regional/webacl/<name>/<id>`) | The shared ACL, associated with the pool; nothing else is created. Deploy it once per account and Region with auth-kit's `createSharedAuthWebAcl` (its README, "WAF: one web ACL for all your sites"); its rule modes are set there. The personal account's is `auth-kit-shared-user-pools` (stack `AuthKitSharedWaf`). |
| `"own"` | A web ACL for this pool alone (about $7 a month): for a site alone in its account, or the first one before the shared ACL exists. The sign-in rule counts first (after about a week of sampled requests, set `signInRule: 'block'` in `amplify/web-acl.ts`; auth-kit README, "Count first, then block the sign-in rule"); the overall per-IP rule blocks from day one. |
| `null` (the template) | Nothing yet. Sandboxes need no web ACL; a branch deploy fails synthesis until you choose. |

The preflight checks that the ARN is a REGIONAL web ACL in the config's own account and Region. Turning WAF off entirely takes `waf: false` and `acknowledgeNoRateLimit: true` in `amplify/auth/resource.ts`: Cognito doesn't lock out wrong emailed codes.

**pnpm instead of npm?** npm is what the template ships and tests. To switch: `pnpm import` (converts `package-lock.json`; check that auth-kit's entry in `pnpm-lock.yaml` still carries its integrity hash), then `pnpm install`, `pnpm dev`, `pnpm run check`, and in `amplify.yml` replace `npm ci` with `corepack enable && pnpm install --frozen-lockfile`.

### The auth matrix

`test/matrix/` starts the real app under `next dev` with no AWS, through auth-kit's `startMatrixServer`: a local test issuer signs each persona's session, and auth-kit's matrix server mode (behind `@/dev-matrix`, never in a build) trusts only that issuer and answers the way Cognito does from a scripted fixture. Then auth-kit's `assertAuthMatrix` sends every request twice, through the proxy and with the proxy stepped aside (so a route that leans on the proxy for its 401 fails), and checks coverage against the build's route manifest: a route without a row fails, and so does a row for a route that doesn't exist.

- **Routes:** `/`, `/sign-in`, `/signed-out`, `/account`, `/account/authenticator`, `/account/sign-in-method`, `/app`, `/app/projects`, `/app/projects/:id`, `/admin`, `/admin/people`, `/admin/activity`, `/admin/settings`, `GET` and `POST /api/projects`, `GET` and `PATCH /api/projects/:id`, `GET` and `PUT /api/projects/:id/access`, `POST /api/auth-kit/account-notice` (every signed-in account may ask, the chooser's code-only account and a password user before the authenticator step included; under the matrix the notice is accepted and dropped); on sites that take them, `/sign-up`, `POST /api/auth/sign-up`, `/request-access`, and `POST /api/auth/request-access` (every persona gets the same answer).
- **Seeded access:** before the rows run, `admin` (Admin – content & people) creates project A through the API, which makes them its Manager, and gives `member` the Contributor role, `manager` the Manager role, and `reader` the Reader role. So on project A the member (Contributor) sees and edits but can't share (403), the reader sees but can't edit or share (403), the manager (a member with no site role) does everything, the second member gets 404 everywhere, Admin – view only sees it but can't edit it (403), Admin – content only edits it but can't share it, and admins who manage people do everything. Edits and access changes re-read the person live, so the demoted admin gets 404 there.
- **Personas:** anonymous, member, a second member, the project's `manager` and `reader`, one per admin role (`adminView`, `adminContent`, `admin` for Admin – content & people, `superadmin`, `owner`), and five lifecycle cases: a password user without an authenticator (sent to setup, 403 from APIs), a demoted admin (the token still says admin; admin pages re-read live and refuse), a disabled admin and a signed-out-everywhere session (Cognito refuses their tokens, so every check fails), and `codeOnlyMember` (auth-kit's `EMAILED_CODE_ONLY_MEMBER`: an invitee with only emailed codes, sent to the chooser page and refused by APIs with 403 `first_credential_required`; only `/account/sign-in-method` lets it in). On sign-up sites, `newMember` (auth-kit's `FRESH_SIGN_UP_MEMBER`) too, held to a member's answers on every row.
- **Also checked:** an account with only emailed codes is sent to the chooser page and refused by APIs; the notice route refuses another origin, non-JSON, and an event it doesn't know; sign-in redirects carry a safe return path; lists are filtered on the server (the member's list has project A as Contributor, the second member's doesn't, every admin's does); the project page shows "Who has access" to everyone who can see it and "Share this project" only to its Managers; the only Manager can't demote themselves (409 `last_manager`); a POST from any origin but the configured one gets 403; bad input gets 400/415; a forged token is refused; private responses are `no-store`; every script tag carries the request's CSP nonce, and the proxy's redirects carry a fresh one; My account shows from the first paint (the authenticator gate follows the page's guard); "Sign in as…" is closed without `ALLOW_DEV_SIGNIN=1`.

Server actions aren't in the route manifest; `test/unit/actions.test.ts` covers them.

## Security headers

`proxy.ts` sends a per-request Content-Security-Policy through auth-kit's `nonceCspHeaders`, on every response it answers (sign-in redirects and refusals too): scripts only with that request's nonce (`'strict-dynamic'`, no `'unsafe-inline'`, no `'unsafe-eval'` outside `next dev`), no framing, no plugins, and network access only to this site, Cognito, and the breached-password check. Amplify's tokens live in cookies page scripts can read, so this policy is what keeps an injected script from running. It needs every page rendered per request, which the root layout does (`connection()`), and which private pages need anyway. `next.config.ts` adds HSTS, `nosniff`, `X-Frame-Options: DENY`, a strict referrer policy, COOP, a Permissions-Policy, and a nonce-free baseline CSP for anything the proxy doesn't handle. Details in `lib/security-headers.ts`.

## Email

All auth email goes through SES from the site's `sign-in@` mailbox ([The sender and the help address](#the-sender-and-the-help-address)), and it matches the sign-in card (auth-kit ADR 0024; register E4a): the family's sender name ("{Site} (UNC)" on a work site, the site's name alone on a personal one), the help address in effect as Reply-To, no letterhead, the code first in code emails with "Only enter codes at {domain}" (each code works for 10 minutes, register A7), and a footer that repeats the card's identity sentence, then "Help: {address}." (personal sites: the help line alone).

| Email | Sent by | Layout and footer |
|---|---|---|
| Sign-in code, the first code of a sign-up, password reset, the code to a new address | Cognito, worded by the custom message trigger (`amplify/auth/custom-message/`) | yes; Reply-To and help line: the configured address |
| Invites (the People page's, an approved request's, a project Manager's) | auth-kit's SES mailer (`lib/email.ts`, `lib/admin.ts`, `lib/resource-actions.ts`); replies go to the inviter | yes |
| The owner's alerts (Super admin granted, ownership transferred, the help address changed), the admins' alert about a Manager's invite | auth-kit's SES mailer, re-laid in the card's layout (`lib/email.ts`) | yes |
| Account-change notices, every site ("A passkey was added to your account", "Your password was changed"; register A10): to the account's own address, right after the change, when the screens ask (the card then says "We've emailed you a note about this.") | auth-kit's notice route (`app/api/auth-kit/account-notice/route.ts`, `lib/accounts.ts`): signed-in accounts only, same origin, a passkey notice checked against the account's passkeys, limited per account | yes |
| Account notices on sign-up and request sites ("You already have an account", email changed, account deleted) | auth-kit's account routes and self-service actions (`lib/accounts.ts`) | yes |
| The request digest (request sites) | auth-kit's daily job (`amplify/backend.ts`) | yes |
| The owner's unused-invite warning | auth-kit's hourly sweep (`amplify/backend.ts`) | yes |
| Grant and removal alerts | `lib/alerts.ts`, through the site's mailer | yes |

## The sign-in page and its backdrop

The sign-in card is the same on every site: auth-kit's `SignIn` is the whole card, in the approved words (Card Studio v4; auth-kit ADR 0024), and a site is recognizable by its family's theme and its backdrop, the art behind the card (auth-kit ADR 0021). The backdrop is decoration for recognition and delight, never a security check: nothing asks anyone to look for the picture.

- **The card** (`app/sign-in/page.tsx`): email first; then **Continue** opens "Use your passkey" only where this browser remembers a passkey sign-in for that address, and otherwise **"How do you want to sign in?"**: **Use a passkey** (recommended), **Use a password**, **Email me a code** (register A5a: no first-visit "no passkey found"). The memory is auth-kit's passkey hint: salted hashes in this site's `localStorage`, never sent to the server, set after a passkey sign-in or a new passkey and cleared when My account removes the last one; the screens and the server traffic stay the same for every address until the person chooses (ADR 0018). Before passkeys are on, Continue goes to "Enter your password". "Use a password instead" and "Email me a code instead" are always offered; **Continue**, then **Sign in** on the step that finishes. "Trouble signing in?" opens six help screens that name the help address and say "Never send a password or code."; the line under the form says how this site gives out accounts (`accountCreation`); the foot carries the family's identity line (none on personal sites). Nothing sits above the heading and there's no colored line on top (register E4); the passkey icon is a fingerprint in the family accent (E4d). The card's colors and its 1px edge (computed to reach 3:1 against every backdrop color) come from the family's theme (`lib/theme.ts`, auth-kit's `auth-kit/themes`). Props: `theme`, `help` (the address in effect, read on the server per request), `accountCreation`, `codeLifetimeMinutes`, and, once passkeys are on, `passkey={{ relyingPartyId }}` (`lib/passkeys.ts`), so the passkey window looks the same for every address. The account-change notices are on by default; `notices={{ mounted: true }}` says the route is mounted, so "Forgot your password?" can promise "We'll email you a note when your password changes."
- **The card style** (register E5): `cardStyle` in `site.config.ts`, `'quiet'` by default (a white 380px card, the defined 3:1 edge, a soft shadow, no monogram), or `'monogram'`, `'frosted'`, `'plain'` (no card: a soft, readable column the backdrop fades into, the one exception to the no-fade rule), or `'porcelain'`, as Card Studio draws them. It reaches every card through the site's theme (`lib/theme.ts`).
- **After the first emailed code**, an invitee or a new sign-up must choose a passkey or a password plus authenticator (`/account/sign-in-method`, auth-kit's `ChooseFirstCredential`; no "Not now"), and gets the account-change notice for it; a passkey made there also sets this browser's passkey hint (auth-kit sets it, given `accountName`). The server enforces it: every other page sends them there, and APIs answer 403 `first_credential_required`.
- **The other cards on the backdrop:** `/sign-up` and `/request-access` (auth-kit's `SignUp`, whose name step says **Continue** because choosing how you'll sign in follows it, register A6; and `RequestAccess`), `/signed-out` (`SignedOutEverywhere`, where My account's "Sign out everywhere" lands), and the error and not-found pages (auth-kit's `AuthCard`). All text is inside a card; nothing is written on the backdrop, and nothing fades it around the card. The scene stays light in dark mode.
- **The email hint**: the email field's placeholder, from the family's theme ("name@example.com" for personal sites) or `emailHint` in `site.config.ts` for a site whose people use other addresses. The "Email address" label always shows.
- **The backdrop** is `backdrop` in `site.config.ts`: `{ style, seed, styleVersion, locked: true }`, literal values. `npm run backdrop:pick` starts the dev server (no AWS; the placeholder outputs file if you have no sandbox) and opens `/dev/backdrops`: nine variations behind the real card, a style filter or a mix of all styles, a family preview, a phone or desktop frame, **Shuffle** for nine more, and a large view where **Use this one** writes the choice (the previous file goes to `site.config.ts.bak`, git-ignored) and prints the change in the terminal.
- **Locked means it never changes.** Until there's a choice, the site's name proposes one, which local development draws; a rename would change it, so deploy builds (Amplify sets `AWS_BRANCH`) fail until it's locked, and other builds (CI, a local `next build`) warn. `npm run backdrop:lock` keeps the proposal. auth-kit freezes every released style version, so upgrading auth-kit never redraws it; when a style has a newer version, the picker offers it side by side and only **Use this one** moves you to it.
- **Kept out of production** like the localhost kit: the picker page and its write route are `.dev.tsx`/`.dev.ts` files (they exist only under `next dev`), the route answers 404 unless the request is from the page itself on a loopback host under `next dev`, the picker carries auth-kit's marker so `npm run check:prod-build` fails a build that contains it, and CI checks that the production server answers the dev routes with 404.

## amplify_outputs.json

Generated, never committed (`.gitignore`). Your sandbox writes yours (`npm run sandbox`); each Amplify branch's pipeline writes its own during the build. CI copies `ci/amplify_outputs.placeholder.json`, whose IDs are fake, so builds and tests run without AWS. Code reads it only through `lib/outputs.ts`. Never copy a deployed branch's file to your machine: localhost must only ever talk to a sandbox (the ribbon turns red if it doesn't).

## Tier 3

For sensitive data, set `tier: 3` in `site.config.ts`: refresh tokens drop to 1 day and Cognito threat protection turns on in audit mode (sign-in event logs). The standard also asks for admins on a separate admin pool (its own Amplify backend, MFA required, no emailed codes, `adminPool: true`, invites with `inviteMode: 'temporary-password'`), a private database, a reviewed audit log, and a quarterly access review. See the comments in `amplify/auth/resource.ts`.

## Upgrading auth-kit

```sh
npm i https://github.com/davidyokum/auth-kit/releases/download/vX.Y.Z/auth-kit-X.Y.Z.tgz
gh release download vX.Y.Z --repo davidyokum/auth-kit --pattern 'auth-kit-X.Y.Z.tgz' --pattern SHA256SUMS
shasum -a 256 -c --ignore-missing SHA256SUMS && gh attestation verify auth-kit-X.Y.Z.tgz --repo davidyokum/auth-kit
npm run check
```

Commit the lockfile: it pins the tarball's sha512, so `npm ci` refuses a tarball that changed. Only auth-kit's entries should change; if `npm i` also drops bundled (`inBundle`) entries elsewhere, put them back, or `npm ci` fails on a clean checkout. Read auth-kit's CHANGELOG for breaking changes first.

**A site made before auth-kit 0.1.10** (preview mode, and the card's contrast and words fixed): remove `nameButton` from `SignUp`, if you pass it (the name step now always says **Continue**, register A6); copy `authKitStyles` again (the focus ring's `#2881cd`, Frosted's fill on a dark page, the forced phone layout); and if your site draws the card on a dark page, declare `color-scheme: dark` there, so the Frosted card thickens to 90% white (this template's scene stays light, so it needn't). UNC's new link color (`#006d9b`) comes with the theme. Never import `auth-kit/preview` from code that ships: `npm run check:prod-build` fails a build that bundled it. auth-kit's CHANGELOG (the Migration notes of 0.1.10-alpha and 0.1.10-alpha.1) lists every item.

**A site made before auth-kit 0.1.9** (sign-in@ senders, notices, the shared web ACL, card styles): copy this template's upgrade commit. In short: senders become the site's `sign-in@` mailbox (`email.fromAddress`, or `null` for the family's, which is the only one a personal site may use, `sign-in@yokum.app`; verify a work site's domain in SES first); pass `email.family` to the preset, `site` to `createSesInviteMailer`, and `family` and `helpEmail` to `InviteExpirySweep`'s `ownerWarnings`; deploy `RateLimitTable` on every site (grant and output) and mount `app/api/auth-kit/account-notice/route.ts` with `createAccountNoticeRoute`, then pass `notices={{ mounted: true }}` to `SignIn` and `accountName` to the chooser's `ChooseFirstCredential`; move the user pool's web ACL to `deploy.config.json` `webAcl` (the shared ACL, or `"own"`) with `amplify/web-acl.ts`; on `domains` sites set `siteWaf` and keep `UnverifiedAccountSweep`; add `cardStyle`; set `codeLifetimeMinutes` to 10 (register A7); the personal family's help mailbox is `help@yokum.app`; copy `authKitStyles` again; and add the notice row to the matrix. auth-kit's CHANGELOG (the Migration notes of 0.1.9-alpha through 0.1.9-alpha.3) lists every item.

**A site made before auth-kit 0.1.8** (account creation, the approved card, families as themes): copy this template's changes (`git diff` between its v0.1.7 and v0.1.8 upgrade commits is the worked example). In short: set the help address (`email.replyTo`, a role-based mailbox; the preset refuses a person's own address); add the custom message trigger (`amplify/auth/custom-message/`) and pass `triggers: { customMessage }` to `standardAuthProps`; add `accountCreation` and `codeLifetimeMinutes` to `site.config.ts` and the preset; deploy `SiteSettingsTable` (and the account-creation tables your mode needs) with their grants and outputs; render `SignIn` alone with `help`, `theme`, `accountCreation`, and `codeLifetimeMinutes` (remove the old card wrapper, owner line, and footer); add `/account/sign-in-method` with `ChooseFirstCredential` (no `onSkip`); add `/admin/settings`; give the matrix `codeOnlyMember` and the chooser row; and copy `authKitStyles` again (the card's styles are in it now). The custom message trigger also refuses email changes made through Cognito's own API, so check nothing of yours relied on that.

**A site made before resource roles** (auth-kit 0.1.7: per-item records checked with `requireRecordAccess`, deprecated since then but still in auth-kit 0.1.10-alpha.1): add `ResourceAccessTable` to `amplify/backend.ts` with its grant and output, declare your types in `lib/resources.ts` and pass `resources` to `createServerAuth` (`lib/auth.ts`), give each record's owner a Manager role on it (a one-time script through `resourceActions().create`), then move each check to `requireResourceRole` and pass `removeResourceMemberships` to the People actions. This template's projects are the worked example; auth-kit [ADR 0022](https://github.com/davidyokum/auth-kit/blob/main/docs/decisions/0022-resource-roles.md#migration) has the steps.

**A site made before the site-wide roles** (groups `superadmin`, `admin`, `editor`, `viewer`): the next deploy deletes `admin`, `editor`, and `viewer` and their memberships, so write down who held each first. Map `superadmin` → `superadmin` (and add one person to `owner` in the Cognito console), `admin` → `admin-content-people`, `editor` → `admin-content`, `viewer` → `admin-view`, then re-grant from the People page. Copy this template's `lib/capabilities.ts`, `personas.json`, and `/admin` pages as the starting point. auth-kit [ADR 0020](https://github.com/davidyokum/auth-kit/blob/main/docs/decisions/0020-site-wide-roles.md#migration-from-superadmin--admin--editor--viewer) has the steps.

## Verified on a live deploy, and what's left

A private demo made from this template (an Amplify branch on the personal account) first checked these on 2026-10-17, on auth-kit 0.1.1-alpha, when the sample items were tickets (projects since 0.1.7):

- The backend deploys on an Amplify branch: preset, audit log, tickets table, and compute role. The pool came up with the standard's settings (auth-kit README, "Verified on a live pool").
- Amplify accepts the compute role (`amplify.amazonaws.com` trust), and IAM's policy simulator allows the People page's Cognito calls on that pool only, `ses:SendEmail` on the site's identity only, and on the audit log `PutItem` and `Query` only.
- `/sign-in` renders with no console errors or CSP violations. Every response carries the nonce CSP, HSTS, and the other headers. Pages redirect to `https://…/sign-in?next=…` and `/api/tickets` answers 401. `/api/dev/sign-in` answers 404 and `check-prod-build` passes in the build. Forged tokens get 401 `invalid_token`.
